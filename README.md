# ☕ Coffee Capsule — Business Insight

A self-contained Business Intelligence application for the synthetic coffee-capsule
plant dataset (3 lines, 51 machines, 1-minute sensor data over a full year,
~26.8 M rows in Parquet). It uses **DuckDB** to run a library of complex analytical
SQL directly against the Parquet lake and a **Streamlit + Plotly** UI to explore
the results interactively.

## Architecture

```
Parquet lake  ──►  DuckDB warehouse            ──►  Streamlit dashboard
(../coffee_        views over parquet +              KPI cards, trends,
 capsule_          materialised aggregates &         Pareto, heatmaps,
 dataset/)         fact tables (init_db.py)          predictive maint.,
                   + 19 analytics SQL queries        SQL explorer
```

- **`sql/01_raw_views.sql`** — views over the parquet files (no copy): `raw_sensor`,
  `dim_machine`, `dim_product`, `raw_schedule`.
- **`sql/02_build_aggregates.sql`** — heavy one-time roll-ups into compact tables:
  `agg_machine_hour`, `agg_machine_day`, `agg_line_product_day`,
  `fact_downtime_episode`, `fact_changeover_episode` (gaps-and-islands).
- **`sql/analytics/*.sql`** — 19 self-documenting complex queries (see below).
- **`app/`** — DuckDB access layer (`db.py`) and the dashboard (`dashboard.py`).
- **`scripts/init_db.py`** — builds the warehouse from the parquet lake.

## Quick start

```powershell
cd coffee-bi
pip install -r requirements.txt

# If the dataset lives elsewhere, point to it (defaults to ../coffee_capsule_dataset):
# $env:COFFEE_DATA_DIR = "C:\path\to\coffee_capsule_dataset"

python scripts/init_db.py          # build coffee_bi.duckdb (one-time, ~seconds)
streamlit run app/dashboard.py     # open the UI
```

## Dashboard tabs
- **Overview** — rolling 7-day OEE, state-utilization stack, hour×weekday heatmap.
- **OEE & Performance** — line/machine OEE, availability/performance/quality, bottlenecks.
- **Reliability & Downtime** — downtime Pareto (with cumulative %), MTBF vs MTTR.
- **Quality & Output** — output by product, yield, worst offenders, changeover matrix.
- **Energy & Cost** — daily cost, kWh per 1,000 capsules, energy by product.
- **Predictive Maintenance** — risk ranking, vibration exceedance, degradation↔reject
  correlation, temperature anomalies, maintenance schedule.
- **Machine Explorer** — full machine master data.
- **SQL Explorer** — run any saved query or your own SQL, download CSV.
- **🤖 Agent** — run the efficiency & production-planning agent and view its
  diagnosis, plan, schedule and reasoning trace.

## 🤖 Agentic layer (`agent/`)

A tool-using agent that **analyzes the sensor data, quantifies inefficiencies,
and generates a production plan**. It runs fully offline on the deterministic
engine; if LLM credentials are present it adds an executive narrative.

```powershell
python -m agent.run_agent                                   # 28-day plan, auto narrative
python -m agent.run_agent --horizon 42 --growth 1.10        # custom horizon/demand
python -m agent.run_agent --demand STRONG=4e7,MILD=3e7,DECAF=2.5e7 --no-llm
```

Outputs (to `agent_output/`): `efficiency_report.md`, `findings.json`,
`production_plan.json`, `production_schedule.csv/.parquet`.

### Scenario optimizer (MILP)

The agent can **optimize** the plan with a real mixed-integer program
(`agent/optimizer.py`, PuLP + the bundled CBC solver) instead of a fixed plan.

```powershell
# maximize demand fulfilment under a €50k energy cap
python -m agent.run_agent --optimize --objective fulfilment --max-energy-cost 50000

# maximize gross margin, no Sunday overtime allowed
python -m agent.run_agent --optimize --objective margin --no-overtime
```

**Decision variables** (per line × product × day over the horizon): production
quantity `x`, campaign assignment `y` (≤1 product per line-day, binary), Sunday
**overtime** `otd` (binary), a continuous **OEE-uplift investment** `U` (capex per
point, linearised on Sundays via McCormick), and **off-peak** production `opx`
(cheaper night tariff, capacity-limited). **Constraints:** per-line daily capacity,
demand caps, off-peak window, optional energy-cost cap and min-fulfilment floor.
**Objectives:** `margin | fulfilment | energy_cost | balanced`. A genuine **Pareto
frontier** (fulfilment ↑ vs energy cost ↓) is generated by the **ε-constraint**
method (repeated solves under tightening energy caps). Typical solve: ~6–10 s for
the full frontier. Outputs `optimizer_scenarios.csv` + `optimizer_result.json`;
the dashboard **🤖 Agent** tab has a *Scenario optimizer (MILP)* panel with the
Pareto scatter, frontier table and optimal line×product production.

**How it works** (`agent/`):
- **`tools.py`** — read-only warehouse toolbox (named queries, ad-hoc SQL, line
  efficiency waterfall, capacity, demand baseline). Also exposes `TOOL_SPECS`
  for LLM function-calling.
- **`analyzers.py`** — `diagnose()` produces ranked, euro-quantified `Finding`s:
  OEE loss waterfall (availability/performance/quality), downtime Pareto,
  bottlenecks, energy intensity, predictive-maintenance risk, changeover waste.
- **`planner.py`** — `build_production_plan()` derives line capacity and product
  demand from the data, then builds a horizon schedule that **minimises
  changeovers** (long single-product campaigns) and **inserts preventive
  maintenance** for high-risk machines on non-production days; reports demand
  fulfilment, utilisation and unmet capacity.
- **`agent.py`** — `EfficiencyAgent` orchestrates a plan→act→observe loop and
  records a transparent trace; swaps in an LLM ReAct/narrative when configured.
- **`llm.py`** — optional Azure OpenAI / OpenAI narrative (`AZURE_OPENAI_*` or
  `OPENAI_API_KEY`); no-op when absent.
- **`report.py`** — markdown / JSON / parquet report rendering.
- **`optimizer.py`** — **MILP** (PuLP/CBC) that decides production, campaign
  assignment, overtime, OEE-uplift investment and off-peak scheduling; objectives
  + constraints; ε-constraint Pareto frontier; returns the winning plan.

Example headline from a run: **€5.5M/yr** of quantified inefficiency
(availability €3.2M, quality €1.2M, changeovers €1.1M) and a 28-day plan of
**45.5M capsules** at 101% utilisation with **0 changeovers** and 9
preventive-maintenance slots.

## Analytics query library (`sql/analytics/`)

| # | Query | Category | Techniques |
|---|-------|----------|------------|
| 01 | Plant KPI Summary | Overview | multi-CTE, cross join, OEE math |
| 02 | OEE by Machine (daily) | OEE | joins, NULLIF guards, LEAST cap |
| 03 | OEE by Line (daily) | OEE | pooled A×P×Q aggregation |
| 04 | 7-Day Rolling OEE Trend | OEE | moving-average window frame |
| 05 | Downtime Pareto | Reliability | window cumulative %, ranking |
| 06 | Reliability MTBF / MTTR | Reliability | episode + uptime joins |
| 07 | State Utilization | Reliability | FILTER aggregates |
| 08 | Utilization Heatmap | Reliability | EXTRACT hour/weekday |
| 09 | Throughput & Yield | Quality | line×product×day grain |
| 10 | Quality Worst Offenders | Quality | RANK window, cost of poor quality |
| 11 | Energy by Line/Day | Energy | multi-CTE, energy intensity |
| 12 | Energy Intensity by Product | Energy | Wh per capsule |
| 13 | Predictive Maintenance Risk | Pred. Maint. | REGR_SLOPE, ARG_MAX, risk blend |
| 14 | Vibration Exceedance | Pred. Maint. | conditional counts vs alarm |
| 15 | Temperature Anomaly (z-score) | Pred. Maint. | 24h rolling mean/std window |
| 16 | Changeover Analysis | Quality | transition matrix, partition % |
| 17 | Maintenance Schedule | Pred. Maint. | DATE_DIFF, overdue status |
| 18 | Bottleneck Analysis | OEE | ARG_MIN, balance ratio |
| 19 | Degradation↔Reject Correlation | Pred. Maint. | CORR() per machine |

## Configuration
Edit `config.py` or set env vars: `COFFEE_DATA_DIR`, `COFFEE_DB`, `ENERGY_PRICE`,
`CAPSULE_COST`, `VIB_ALARM`.

## Notes
The DuckDB warehouse (`coffee_bi.duckdb`) is a rebuildable artifact and is
git-ignored; regenerate it any time with `python scripts/init_db.py`.
